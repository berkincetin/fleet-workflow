## Notable issues resolved (symptom → root cause → fix)

- **GitHub 422 "no commits between main and agent/X" on `open_pr`**: `create_branch` only points a new ref at the base branch's existing commit — a PR against a branch with zero new commits is structurally rejected by GitHub. Root-caused by reproducing the exact 422 body standalone against the real API. Fixed by adding `github.commit_file` (write:internal) and calling it right after `create_branch`, matching the Dev Agent's own task wording ("implementation draft") rather than being an ad hoc workaround.
- **GitHub 422 "Reference already exists" on a second live run of the same ticket**: the LLM's `branch_suffix` is near-deterministic for the same ticket wording, so repeated runs collided with their own prior branch on the persistent sandbox repo. Fixed by suffixing every branch name with a run-unique `uuid4().hex[:8]` token.
- **A raised `slack.post()` would have crashed the whole resume call *after* the PR had already opened successfully** — caught before it ever reached a live test, by reasoning through what an unset `FLEET_SLACK_WEBHOOK_URL` would actually do (`httpx.AsyncClient().post("")` → `UnsupportedProtocol`). Fixed by wrapping `slack_notify` so a notification failure surfaces as `slack_notify_error` in the returned state instead of propagating — best-effort, not a hard dependency of "the PR opened." Locked in with a unit regression test before the live e2e test was ever run.
- **`sensitivity` keyword collision** (`agents.analytics.service`): `chat.py` passed `sensitivity=agent.sensitivity` through `**meta`, which was forwarded into a call that also hardcoded `sensitivity="internal"` — a `TypeError`, caught only by the live chat-endpoint integration test, never by unit tests (which never exercised `**meta` containing `sensitivity`). Fixed by giving `generate_sql` its own explicit `sensitivity` parameter, matching the established pattern in `fleet_rag.query.service.answer_query`.
- **Migration `0007` broke on a fresh testcontainer**: hardcoded `GRANT fleet_readonly TO fleet` assumes the dev compose app-user name; testcontainers' generated superuser has no such role. Fixed by granting to `CURRENT_USER` instead.
- **`evals/runner.py --agent dev_agent` failed with an empty `Bearer` auth header**: the eval runner is a standalone script, never picks up `.env` (this repo has no `pydantic-settings` auto-load and no other Python-side dotenv loading). Fixed by adding the same `.env` fallback parser already used in the live GitHub integration test.
- **mypy cross-package friction, documented not silently worked around**: adding a `py.typed` marker to `apps/runtime/core/` (the textbook fix for `pg_ro.py`'s cross-package exception subclassing showing as `Any`) fixes that error but breaks mypy's module-identity resolution when `apps/runtime` and `apps/mcp`/`apps/api` are checked together — confirmed the actual `make lint` gate is unaffected either way (its `mypy apps packages` invocation already fails immediately on the `packages` arg, pre-existing and advisory). Used two narrow `# type: ignore[misc]` instead of chasing a fix that trades one false positive for a different one.

## Deviations / deferrals

- **Analytics' "knowledge" is a static Python glossary, not a real RAG collection** — day-0 scope is 2 fixture views, which doesn't warrant standing up Qdrant/ingestion for. `SemanticLayer`'s shape is designed so a future real-RAG swap wouldn't change the SQL generator's call site.
- **Jira/Slack have no live integration test** (unlike GitHub) — no real Jira Cloud or Slack workspace credentials existed this session; both are built to the same real-transport-option shape (`RestJiraBackend`/`SlackWebhookSender`) as `RestGitHubBackend` and will need the same live-smoke treatment once credentials exist.
- **The approval-resume mechanism is Dev-Agent-specific**, not a generic per-agent registry — Dev Agent is the only interrupt-producing agent this sprint (Analytics/Support Copilot have no write tools), so a registry abstraction has no second caller to prove itself against yet. A second interrupt-producing agent is the natural trigger to extract one.
- **"All steps in one Langfuse trace" (5.5's AC) was not separately re-verified this sprint** — the mechanism is present (same gateway-client trace-forwarding fixed in Sprint 4), but no dedicated trace-correlation check like 4.3's was run for a Dev Agent run specifically. Flagged as unverified rather than claimed.
- **The department scenario's literal "refusal test for `users_raw` table" AC** anticipated `pg_ro`'s allowlist refusal firing directly from a live NL question; live testing showed the SQL generator's own semantic-layer grounding usually intercepts these first via a clarifying question instead (arguably a stronger guardrail — it never generates the forbidden SQL at all). Both mechanisms exist and are tested; the eval dataset's `must_refuse_or_clarify` assertion reflects the real observed behavior rather than silently reinterpreting the AC.
- **~28 branches accumulated on the user's sandbox GitHub repo** from this sprint's repeated live testing and eval runs. Left as-is (disposable sandbox, cleanup not requested).

## Cross-cutting rules honored

- **Rule 1** (LLM calls only via the gateway client): Analytics' SQL generation and Dev Agent's planning both go through `core.llm.client.LLMClient`; no provider SDK anywhere new. GitHub/Jira/Slack MCP servers use plain httpx against their own REST/webhook APIs, not an LLM call site.
- **Rule 2** (sensitivity routing enforced): unaffected this sprint — no new cross-sensitivity paths introduced.
- **Rule 3** (external side effects go through MCP servers with a declared `risk_class`): every new tool (pg_ro, ocr, email, internal-mock, jira ×2, github ×3, slack) declares one of the three TRD §9 classes; `github.open_pr` and `email.send` are always `write:external` with no bypass, proven live for GitHub.
- **Rule 6** (cross-cutting middleware never special-cased): Dev Agent's graph still runs through `killswitch_gate` first, same as `core.graph`'s agents, even though it's a dedicated graph rather than `build_graph()` — the killswitch check wasn't skipped just because the flow is custom.
- **Rule 7** (migrations only via Alembic; `fleet_readonly` stays read-only): migration `0007` is the only new one this sprint, and it only grants role *membership*, never expands what `fleet_readonly` itself can do — proven live via the `SET ROLE` + `DELETE` rejection test.
- **Rule 9** (tests accompany code): every new module has unit coverage; every task has live verification against real infrastructure (real Postgres/mailpit/GitHub sandbox, real gateway calls, real LangGraph checkpoint resume).
- **Rule 10** (costs are a feature): Analytics' SQL generation and Dev Agent's planning both deliberately use `reasoning()` (judgment/generation call-sites per TRD §4.3), not `utility()` — plan/SQL quality matters more than cost at this call volume.
