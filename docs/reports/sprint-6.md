## Notable issues resolved (symptom → root cause → fix)

- **oauth2-proxy redirected to the container-internal `keycloak:8080` instead of the browser-reachable `localhost:8080`**: OIDC auto-discovery resolves every endpoint from Keycloak's own issuer metadata, stamped with whatever hostname Keycloak was reached at internally. Fixed by skipping discovery and supplying `--login-url` (host-facing) separately from `--redeem-url`/`--oidc-jwks-url` (container-internal, server-to-server).
- **`oidc: id token issued by a different provider`**: Keycloak stamps the ID token's `iss` from the browser's actual base URL, not a fixed server value — `--oidc-issuer-url` had to match that, even though it's otherwise irrelevant to how oauth2-proxy reaches Keycloak.
- **`audience claims [aud] do not exist in claims`**: Keycloak 26 omits `aud` by default (confirmed via the raw claims dump — only `azp` present), the same root cause `fleet_api/auth.py` already tolerates via `azp`, but oauth2-proxy has no such fallback. Fixed at the source with an explicit `oidc-audience-mapper` protocol mapper on the `n8n` Keycloak client, not a workaround flag.
- **A latent, Sprint-1-era gap: `.env` wasn't reliably read by `docker compose -f infra/compose/docker-compose.dev.yml`** when invoked without an explicit `--env-file` — every prior `.env`-sourced var happened to have a working fallback or be optional, so this was silently broken until n8n's Fleet API key (no safe default) needed it. Fixed the `Makefile`'s `COMPOSE` variable to always pass `--env-file .env` explicitly — a real fix to a real pre-existing bug, not a Sprint-6-scoped workaround.
- **n8n webhook 404 "not registered" despite `active: true`**: a hand-authored workflow JSON's webhook node lacked the `webhookId` field n8n's own UI always generates, causing it to register a dynamic workflow/node-scoped path instead of the intended static one. Root-caused by inspecting n8n's own `webhook_entity` table directly. Fixed by generating a real UUID and committing it in `workflows/invoice-intake.json`.
- **Vendor-name extraction "failures" that were actually correct OCR**: a small local vision model reading rendered Turkish text sometimes returns more/less precise Turkish orthography than the eval fixture's own (inconsistently ASCII-folded) spelling — byte-identical matching was the wrong bar. Fixed with a fuzzy, Turkish-transliteration-aware vendor comparison (`_vendor_reasonably_matches`); `po_number`/`amount` stay exact-match since those are unambiguous.
- **Eval dataset design bug, not an agent bug**: an early version of the invoice eval dataset reused only 5 PO numbers across 12 "clean" cases, and the agent's own duplicate-detection guardrail correctly flagged cases 6–12 as duplicates of 1–5 within the shared batch. Fixed by expanding the fixture PO table to 15 distinct rows.

## Deviations / deferrals

- **`invoice_intake` scope + `require_user_or_service_scope`**: not anticipated in the original task text, discovered live when the invoice-intake webhook workflow tried to call `/v1/invoice-agent/runs` (Keycloak-bearer-only at the time) with no Keycloak session at all. Generalized the auth to accept either credential kind rather than special-casing n8n, matching how 6.1's `/v1/service/*` routes already worked.
- **The invoice-intake workflow's `Respond: blocked` (422) branch was built and wired but not separately live-webhook-tested** — only the golden matching-invoice path was driven through the real webhook this session; the underlying `blocked_reason` mechanism is unit/integration-tested at the API level, just not through the n8n workflow specifically.
- **`n8n-main`'s `:5678` port stays published in compose** even though the intended human entry point is exclusively the `:5679` proxy — needed for the worker's/proxy's own reach and for local debugging; a real deployment would put `n8n-main` on a compose-internal-only network.
- **The pre-existing `platform_admin`/`dept_admin` vs. seeded-realm role-string gap** (first logged Sprint 3) now also blocks live-testing `api_keys_admin.py`'s issuance endpoint directly — worked around identically to every other admin router affected: the *enforcement* path is proven live via directly-seeded rows, only the issuance endpoint itself is untested live. This gap now affects six admin routers and is worth fixing directly the next time it blocks something that can't be worked around.
- **Invoice Agent's duplicate-detection is batch-scoped** (`seen_po_numbers`, an in-memory set per graph build/eval run), not a persisted table — correct for this sprint's literal AC ("duplicate invoice fixture") but would need a real table to catch duplicates across arbitrarily-separated real-world submissions in production.

## Cross-cutting rules honored

- **Rule 1** (LLM calls only via the gateway client): Invoice Agent's field extraction goes through `core.llm.client.LLMClient`; no provider SDK anywhere new.
- **Rule 3** (external side effects go through MCP servers with a declared `risk_class`): `erp.create_draft_entry` is always `write:external`, no autonomy path, matching the department scenario's "approval-gated forever" rollout note.
- **Rule 4** (retrieved/tool content is untrusted): `po_lookup.py` explicitly never string-interpolates the LLM-extracted `po_number` into SQL, fetching the whole allowlisted table and matching in Python instead — documented and unit-tested (`test_lookup_never_interpolates_the_untrusted_po_number_into_sql`).
- **Rule 6** (cross-cutting middleware never special-cased): Invoice Agent's graph runs through `killswitch_gate` first, same as every other agent, even as a dedicated graph.
- **Rule 7** (migrations only via Alembic): `0008_api_keys` is the only new migration this sprint.
- **Rule 9** (tests accompany code): every new module has unit coverage; every task has live verification against real infrastructure (real Keycloak OIDC flow, real n8n queue-mode execution, real Postgres, real gateway calls).
- **Rule 10** (costs are a feature): Invoice Agent's field extraction deliberately uses `reasoning()`, not `utility()` — structured extraction from noisy OCR text is a judgment call-site, matching the same choice already made for Dev Agent's planning and Analytics' SQL generation.
